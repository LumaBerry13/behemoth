# Behemoth — Design & Project Documentation

Oct 6, 2026 · @Nitesh Mali

## 1. Summary and how to use this document

Behemoth is a boss framework built on the Minecraft Bedrock Script API, shipped as a separate library pack: players install it once, and boss packs (one JS config per boss plus the standard connector, the model and animations) register their bosses with it over script events. Skills, triggers, targeters and conditions are plug-in modules registered in manager files. A Python converter turns MythicMobs + ModelEngine bosses into Behemoth boss packs. Status (Oct 6, 2026): M1 and M2 done (Dark Knight tested in-game, including reload). M3 converter largely done. M4 in progress: reset/leash, profiler, the §13 module list, the library split with cache-first registration (D1), the `/behemoth` chest-UI menu and the shared particle library are implemented; timeline markers outstanding.

This document is the single source of truth for the project. It is written so that a human or an AI assistant (Claude chat or Claude Code) with no prior context can understand the design and continue the work.

**Reading order for a newcomer:** sections 1–2 (what and why), 3 (platform limits that shaped every decision), 4–9 (the design), 13–14 (what to build first and in what order), 15 (what is still undecided), 17 (rules for continuing the work).

**Confidence markers used throughout:**

- **\[VERIFY\]** — an API name, signature or engine limit recalled from memory that must be checked against the current `@minecraft/server` typings or Microsoft Learn docs before use. Never treat these as facts.
- **\[DECIDED\]** — a design decision already agreed.
- **\[OPEN\]** — not yet decided; listed again in section 15.

### Glossary

| Term | Meaning |
| --- | --- |
| MythicMobs (MM) | Java server plugin for custom mobs and bosses, configured in YAML (mobs.yml, skills.yml, drops.yml, items.yml). |
| ModelEngine (ME) | Java plugin that renders Blockbench models with bone animations, per-bone hitboxes and mounts. |
| Behemoth (BHM) | This project: the Bedrock port of the MM workflow. |
| Script API | Bedrock's JavaScript API, mainly the `@minecraft/server` module, running inside a behavior pack. |
| BP / RP | Behavior pack (server logic, entity JSON, scripts) / resource pack (models, animations, textures, particles, sounds). |
| Boss config | One JS file per boss (e.g. `darkknight.js`) describing health, phases, skills and settings. Replaces MM's YAML. |
| Mechanic | One action a skill performs (damage, leap, particle, summon). A plug-in module. |
| Targeter | Selects who or where a mechanic affects (`@self`, `@target`, `@PlayersInRadius`). A plug-in module. |
| Condition | A boolean check gating a skill (health below 50%, distance, chance). A plug-in module. |
| Trigger | The event that starts a skill (`~onSpawn`, `~onDamaged`, `~onTimer`). A plug-in module. |
| Skill line | One configured use of a mechanic: mechanic + options + targeter + trigger + conditions + cooldown + children. |
| Behemoth-ready stub | The standard set of components, component groups, events and properties every boss entity JSON must contain so the framework can control it. Section 5. |
| Baked track | Pre-computed per-tick position of a bone during an animation, generated by the converter. Section 6. |
| Converter | Offline Python tool that reads the model and animation files and generates baked tracks, an entity patch and a config skeleton. Section 9. |
| Tick | 1/20 second. All framework timing is in ticks. |
| Threat table | Per-boss record of damage dealt by each player, used for targeting. |

## 2. Goals, scope and non-goals

The goal is a reusable boss engine: write the framework once, then add a new boss by dropping in one config file plus its model and animations.

### Goals

- **Plug-and-play bosses.** Paste `darkknight.js` into the configs folder, add one import line in the boss manager, and the framework controls the boss as configured.
- **Plug-and-play modules.** Each mechanic, targeter, condition and trigger is its own file, registered in a manager file. New MythicMobs concepts are added as new modules over time.
- **MythicMobs parity for common features.** Recreate the subset real boss packs use (section 12), not all of MythicMobs.
- **ModelEngine-like behaviour** through animation playback, baked bone tracks and entity properties (sections 5–6).
- **Efficiency.** Every feature must have a cheap runtime path; heavy work moves to the offline converter.
- **A documented alternative for every platform limit** (section 3).

### Inputs per boss

- An entity (BP + RP) with model, texture and all animations, but no animation controller. Spawned as-is, it just stands there.
- Typically sourced from purchased Java ModelEngine + MythicMobs packs: the `.bbmodel` is imported into Bedrock with Blockbench (Minecraft Entity Wizard plugin) and animations are linked manually. \[DECIDED 2026-10-06: the Java → Bedrock model conversion stays manual (owner, in Blockbench); the converter only reads the `.bbmodel` for timeline markers.\]
- The MM YAML files (mobs, skills, drops, items) are the behavioural reference used to write the JS config.

### Outputs per boss

- The boss's JS config.
- Generated per-animation data files (baked tracks, lengths, hit frames) from the converter.
- A patched entity JSON containing the Behemoth-ready stub.

### Non-goals (v1 and likely beyond)

- 100% MythicMobs compatibility; Java-server-only features such as placeholders, economy hooks, holograms, packet disguises and custom GUIs.
- MythicCrucible-style custom items with abilities (a possible separate framework, section 16).
- True per-bone hitboxes, segmented multi-entity bodies, riding on arbitrary bones.
- Running unconverted YAML at runtime. YAML is a reference only; an optional YAML→JS generator may come later.
- Beta / experimental Script APIs.

The Script API can run all of MythicMobs' logic, but it cannot change an entity in ways the entity JSON did not prepare for, and it has no access to model bones. This table is a living registry: every newly found limit gets a row, a workaround and a status.

### API notes (all \[VERIFY\] before use)

- **Animation:** `entity.playAnimation(name, options)` takes options such as next state, blend-out time, a Molang stop expression, a controller name and a player list.
- **Movement:** `applyImpulse`, `applyKnockback` (signature changed in 2.x), `teleport`, `setRotation`. Movement can be frozen by setting the movement attribute's current value to 0.
- **Damage and health:** `applyDamage` with cause and damaging entity; health via the health component's current value.
- **Query:** `dimension.getEntities` with query options (location, maxDistance, families, tags, type); entity and dimension ray methods.
- **Effects:** `dimension.spawnParticle` with a Molang variable map, `playSound`, `onScreenDisplay`, `/camerashake` through `runCommand`, camera fades.
- **Projectiles:** `spawnEntity` plus the projectile component's `shoot()`.
- **Persistence:** `setDynamicProperty` / `getDynamicProperty`.
- **Commands:** custom command registration during startup in 2.x.
- Biome and light-level queries have moved between versions.

## 4. System architecture

The framework is five layers, and each layer only talks to the one below it. Boss configs and modules are data and plug-ins; the core never names a specific boss or mechanic.

1. **Configs and generated data** — boss config files and converter-generated animation data.
2. **Modules** — mechanics, targeters, conditions, triggers. One file each.
3. **Registries and managers** — `BossManager` (binds configs), `SkillManager` / registries (bind modules).
4. **Core runtime** — boss instances, scheduler, event bus, threat table, persistence, config validator.
5. **Adapter** — the only code that calls `@minecraft/server` directly.

### Core components

| Component | Responsibility |
| --- | --- |
| Adapter | Wraps every Script API call (spawn, damage, particles, animation, properties, events). A breaking API change is fixed here once. |
| Config validator | Runs at startup. Rejects unknown mechanics, bad options, missing animations, unmet `requires`, with clear log messages. |
| BossManager | Holds the list of imported boss configs; maps entity type ID → config. |
| BossInstance | One per live boss entity, keyed by entity ID. Holds phase, cooldowns, running skills, threat table, current animation and start tick. |
| Scheduler | One central tick loop (`system.runInterval`, 1 tick). Runs delayed skill steps, timers and cooldowns. Every task carries a cancel token tied to its boss instance. |
| Event bus | Converts Script API events into framework triggers; also carries custom signals between skills and bosses. |
| Threat table | Damage dealt per player; drives `@target` selection and retargeting. |
| Persistence | Saves instance state to dynamic properties; restores it on `entityLoad`. |
| Debug tools | Commands, overlay and bone markers (section 11). |

### Plug-and-play rules \[DECIDED\]

- A module registers with `bind("name", ModuleClass)` (mechanics) or `bindCondition("name", ConditionClass)` and equivalents for targeters and triggers.
- One shared singleton per name. Mechanics and conditions are **stateless**; all state lives in the boss instance or the execution context passed in.
- A module declares dependencies in a field, e.g. `requires: ['projectile']`, instead of a code comment. At startup the registry checks every `requires`; a skill whose dependency is missing is disabled with a warning and the rest of the boss still works.
- A boss config declares which modules it uses; the validator checks they are registered.
- No dynamic imports exist, so every config and module is a static import line in its manager file.

### Pack layout \[DECIDED 2026-10-06: framework as a library (D1)\]

Script contexts are per behavior pack, so the framework cannot import JS from another pack. Decision: the framework is a separate library pack, and boss packs register with it over script events (protocol v1).

- **Framework BP + RP (`packs/behemoth`):** runtime, modules, the `/behemoth` menu (chest UI), the boss-pack registrar and its cache. Its UUIDs never change; boss packs depend on them.
- **Boss pack BP + RP:** entity JSON with the Behemoth-ready stub, `scripts/bosses/index.js` (plain-data configs), `scripts/behemoth/connector.js` (identical copy of `connector/connector.js`), `scripts/main.js` calling `connect({ pack, version, minFramework, bosses })`, plus model, animations and textures. The manifest depends on the framework BP.
- **Protocol v1:** packs → `bhm:hello {p, pack, ver, hash, size, min}` and `bhm:part "<pack>|<hash>|<i>|<n>|<data>"`; framework → `bhm:ready`, `bhm:need {pack, hash}`, `bhm:ack {pack, hash, ok, bosses, errors}`. Only script-sent events are accepted. Protocol and `minFramework` are checked, a boss type belongs to the first pack that registers it, transfers time out, and duplicates are ignored.
- **Cache-first:** each accepted payload is cached in the framework's world dynamic properties. After a load or `/reload` the framework restores every cached boss in its first tick (sub-millisecond in tests), then announces `bhm:ready`; packs whose hash matches only receive an ack. A transfer happens only for new or updated packs. A cached pack must say hello within 100 ticks of `bhm:ready`, otherwise it is unloaded and its cache entry deleted (pack removed from the world). Configs whose entity type no longer exists are skipped at install (L35).
- **Compact data:** baked bone tracks are sent as base64 int16 (`{q, n, d}`, decoded by `TrackCodec`), about 4× smaller than JSON numbers (Dark Knight: 26 KB in total).

- **Framework BP:** all scripts, all boss configs, all generated animation data.
- **Framework RP:** shared particle library \[DECIDED 2026-10-07: part of the framework RP, not a separate pack\] (`particles/bhm_*.particle.json` + white textures in `textures/behemoth/particles/`, generated by `tools/particles.py`; colour, size, lifetime, speed, amount, rise and swirl width come from Molang variables set by `modules/shared/particle_vars.js`), render-controller templates, shared sounds.
- **Boss BP + RP (per boss, or merged into the framework packs):** entity JSON with the Behemoth-ready stub, model, textures, animations.
- **Consequence:** configs cannot contain functions (inline custom conditions are no longer supported); boss-specific code would need a call-out mechanic (future).
- **Licensed bosses:** converted bosses become their own boss packs under the git-ignored `private/<Boss>/pack/`; `npm run package` builds their `.mcaddon` into `private/<Boss>/dist/`.

## 5. Behemoth-ready entity stub

Every boss entity gets the same standard stub, because a script can only trigger events and set properties that the entity JSON already defines. Without it the framework is limited to animations, damage, particles and teleports. The converter generates the stub as a patch (section 9). \[DECIDED: hybrid AI controlled by component groups\]

### Component groups and events

Names are proposals; the `bhm:` prefix marks framework-owned items.

| Group | Purpose | Toggled by event |
| --- | --- | --- |
| `bhm:idle` | Stands or wanders; no targeting. | `bhm:set_idle` |
| `bhm:chase` | Vanilla navigation + movement toward the target; attack behaviours removed (scripted attacks only). | `bhm:set_chase` |
| `bhm:frozen` | No movement or navigation; used while casting or during cutscenes. | `bhm:set_frozen` |
| `bhm:invulnerable` | `damage_sensor` that blocks all damage. | `bhm:invuln_on` / `bhm:invuln_off` |
| `bhm:resist_<n>` (optional) | Damage sensor variants for specific causes. | per variant |
| `bhm:despawn` | Clean removal on reset or arena leave. | `bhm:despawn` |

Movement can also be paused without a group swap by setting the movement attribute to 0 (L7).

### Entity properties (script → client visuals)

| Property | Type | Use |
| --- | --- | --- |
| `bhm:phase` | int | Phase-specific visuals (texture, glowing parts). |
| `bhm:visibility` | int or several bools | Part visibility via render controller `part_visibility`. |
| `bhm:anim_speed` | float | Animation speed via `anim_time_update` in RP animations. |
| `bhm:state` | enum | Optional, for client-side looping states. |
| `bhm:idle_state` / `bhm:walk_state` | int | Which idle/walk animation the generated base controller loops (ModelEngine `defaultstate`). Index into config `baseStates`. |

There are engine limits on property count per entity type and enum values per property \[VERIFY\]. Keep the set small and shared across bosses.

### Other required components

- `minecraft:boss` for the boss bar (text updated through `nameTag`).
- Health, collision box, knockback resistance, and scale set to match the boss config.
- Peaceful handling \[DECIDED 2026-10-06, D6\]: the framework removes every Behemoth entity on Peaceful and refuses new spawns (config `allowPeaceful: true` opts out).
- `minecraft:persistent` (or equivalent) so the boss does not despawn naturally \[VERIFY\].

### RP side of the stub

- Render controller that reads `bhm:` properties.
- Animations that need variable speed reference the speed property in `anim_time_update`.
- Locators for any bone-attached client effects (optional; baked tracks are the main method).

## 6. Animation system and bone baking

Animations play through `playAnimation` with no controller, and bone positions come from tracks the converter pre-bakes at 20 samples per second. This replaces ModelEngine's per-bone entities and avoids running forward kinematics at runtime. \[DECIDED\]

### Playback

- The `state` mechanic calls `playAnimation` and records the animation name and start tick on the boss instance.
- The end of an animation is known from its baked length; the scheduler fires an internal `animEnd` event at `startTick + length`.
- Controller names per layer: `bhm_base` (idle/walk), `bhm_action` (attacks), `bhm_overlay` (additive effects). Two calls on the same controller override each other (L4).
- Blend-out time is set per state in the config. During blends, baked positions are approximate.

### Per-animation data file (generated)

One JS module per animation, e.g. `generated/darkknight/attack_slam.js`:

```
export default {
  name: "animation.darkknight.attack_slam",
  length: 40,              // ticks
  loop: false,
  hitFrames: [18, 19, 20], // from Blockbench timeline markers
  markers: { slam_impact: 19 },
  bones: {
    bhm_sword_tip: [[0.0, 2.1, 0.9], [0.0, 2.2, 0.8], ...], // one [x,y,z] per tick, model space, blocks
    bhm_head:      [[...], ...]
  },
  unbakeable: ["head_look"]  // bones whose motion depends on runtime Molang
};
```

### Which bones get baked \[DECIDED 2026-10-06, D5\]

Only the bones the MythicMobs YAML references through `@modelpart`, plus job-file `bone_aliases` and `blades` (blade tips), to keep data small (3 bones × 60 ticks × 3 floats ≈ 540 numbers per animation). No model edits and no bone naming convention.

### Runtime lookup

1. `t = currentTick - startTick`, clamped (or wrapped if looping).
2. Take offset `[x, y, z]` from the bone's track at `t`.
3. Multiply by the entity's scale.
4. Rotate around Y by the body yaw.
5. Add the entity's location.

This is a few multiplications per bone per tick, with no hierarchy traversal.

### Uses

- **Bone-attached effects:** particles or sounds at a bone on a given tick.
- **Attack hit detection:** during hit frames, a sphere around each tagged bone; `getEntities` with a small `maxDistance` around the sphere centre.
- **Weak points:** on `entityHitEntity`, raycast from the attacker's view against the bone spheres at that tick to decide head vs body hits.

### Known inaccuracies and risks

- Client/server drift of \~0.1–0.3 blocks from latency and client-side body-rotation smoothing (L20).
- Molang depending on runtime queries cannot be baked (L13).
- Coordinate conventions to verify \[VERIFY\]: X-axis mirroring between Blockbench and Bedrock geometry, Euler rotation order, and whether `getRotation().y` equals the rendered body yaw.
- **Calibration test (do first):** a debug mode that spawns a particle at every computed bone position each tick. If the particle visibly follows the bone, the math is correct.

## 7. Skill system

A skill runs as: trigger fires → conditions checked → targeter resolves targets → mechanic executes → child skills or delays scheduled. All timing is in ticks. \[DECIDED\]

### Skill line format (earlier agreed shape)

| Key | Meaning |
| --- | --- |
| `m` | Mechanic name |
| `o` | Mechanic options object |
| `t` | Targeter (name + options) |
| `tr` | Trigger(s) |
| `if` | Conditions, ANDed; each supports negation and arguments |
| `chance` | 0–1 probability |
| `c` | Nested child skill lines, for meta-mechanics (skill, randomskill, delay chains) |

Plus per-skill cooldown and a global cooldown (GCD), both in ticks. Skill lines are parsed and validated once at startup, never per execution.

Added 2026-10-06 (Archivist feature pass):

| Key | Meaning |
| --- | --- |
| `delay` | On a line: run it N ticks later without pausing the sequence (MythicMobs `delay=`). |
| `repeat`, `repeatInterval` | On a line: run it N more times, `repeatInterval` ticks apart (default 1), without pausing. |
| `cooldown` | On a child line: skip it while on cooldown (MythicMobs per-mechanic `cd=`). On a skill: the skill cooldown. |
| `targetIf` | On a skill: target conditions (MythicMobs TargetConditions), tested on each inherited target (else the current target); failing targets are dropped, none left = the skill does not run. |
| `… castInstead <skill>` / `… orElseCast <skill>` | Suffix on any condition: cast another skill instead when it passes / fails. |

**Variables:** names carry a scope prefix — `caster.` (default, persisted with the boss), `target.`, `trigger.` (a Behemoth entity's own vars, else an in-memory per-entity store), `skill.` (shared by one run and the skills it calls), `global.` (world property `bhm:vars`). `setVariable` supports `type` (int/float/string/boolean) and `duration` (ticks); `variableMath` evaluates an expression (`x` = current value) with a small safe parser. Initial caster values come from config `variables`. Conditions: `variable`, `varEquals`, `variableIsSet`.

**Placeholders:** any option string may contain `<caster.var.x>`, `<target.var.x>`, `<skill.var.x>`, `<global.var.x>`, `<caster.hp>`, `<caster.mhp>`, `<caster.php>`, `<caster.name>`, `<caster.phase>`, `<caster.l.x>`, the same for `target.`/`trigger.`, and `<random.float.AtoB>` / `<random.int.AtoB>`. They are resolved per execution; numeric results become numbers. Validation substitutes 1 for each placeholder.

### Triggers → Script API sources

| MythicMobs trigger | Source |
| --- | --- |
| `~onSpawn` | `entitySpawn` / `entityLoad` |
| `~onDamaged` | `entityHurt` (after event) |
| `~onAttack` | `entityHitEntity` |
| `~onDeath` | `entityDie` |
| `~onInteract` | `playerInteractWithEntity` |
| `~onTimer:N` | Framework scheduler |
| `~onSignal` | Framework event bus |
| `~onEnterCombat`, `~onChangeTarget`, `~onPlayerKill` | Derived by polling or from hurt/death events |
| Health thresholds / phase change | Derived from hurt events |
| `animEnd`, `marker` (framework extras) | Scheduler, from baked data |

### Targeters (common set)

`@self`, `@target`, `@trigger`, `@PlayersInRadius`, `@EntitiesInRadius`, `@MobsInRadius`, `@NearestPlayer`, `@RandomPlayer`, `@ThreatTable` / highest threat, `@Cone`, `@Ring` / circle locations, `@TargetLocation`, `@SelfLocation` with offsets, `@Bone:<name>` (framework extra, from baked tracks), line-of-sight filters. Built on `getEntities` query options, ray methods and vector math. Added 2026-10-06: `@Origin` (where a projectile / ray trace is), `@Parent` (the summoner), `@RandomLocationsNearCaster` (`@RLNC`).

### Conditions (common set)

Health / health percent, distance, line of sight, chance, has tag, scoreboard value, height / Y level, is in block, time of day, weather, phase, variable compare, target exists, player count nearby, cooldown ready. Biome and light level \[VERIFY API\]. Added 2026-10-06: `fieldOfView{angle;rotation}` (cone centred on yaw − rotation; 90 = the caster's left \[VERIFY\] against MythicMobs), `inCombat`, `varEquals`, `variableIsSet`, `directionalVelocity`, `altitude`.

### Mechanics (common set, \~40)

- **Combat:** damage, basedamage / percent damage, heal, potion effect, ignite, lightning, explosion (scripted, no block damage by default), shield / invulnerable phase.
- **Movement:** leap, lunge, velocity, pull, throw / knockback, teleport, teleport-behind, dash (scripted), freeze, set AI mode (component group swap).
- **Projectiles:** projectile / missile (custom entity or scripted particle projectile), shoot.
- **Visual and audio:** particle, particle ring / sphere / line / helix (shapes), sound, state (animation), set property (visual), message, title / actionbar, camera shake.
- **World:** summon (with caps), block wave / temporary blocks (restored), set block.
- **Flow / meta:** delay, skill / metaskill, randomskill, chained skills, set variable, signal, phase change, aura (repeating effect for N ticks), cancel skill.
- **Added 2026-10-06 (common MythicMobs vocabulary):** `explosion` (no block damage unless breakBlocks + mobGriefing), `shoot` (vanilla projectile entities), `jump`, `threat` (add / set / taunt / clear), `setHealth`, `swap`, `forcePull`, `command` (runs as the boss), `suicide`; `projectile{homing}` = MythicMobs missile. Effect entities (telegraphs, ground effects, slashes) are `kind: "minion"` configs with no AI that remove themselves.

### Execution rules \[DECIDED 2026-10-06, D3: the defaults below\]

| Question | Rule |
| --- | --- |
| Can skills run concurrently? | Yes, but a skill marked `exclusive` takes a casting lock that blocks other `exclusive` skills. |
| Casting lock during animations? | Optional per skill: lock until `animEnd`. |
| Boss dies mid-skill? | Cancel every task with that instance's token. |
| Phase change mid-skill? | Skills flagged `interruptible` cancel; others finish. |
| Target lost mid-skill? | Re-resolve targeter at each step; if empty, skip that step. |
| Delays block other triggers? | No (same as MythicMobs). |

### Threat and targeting

- The threat table adds damage per player from `entityHurt`.
- Scripted skills target the highest-threat valid player.
- Valid = alive, same dimension, within leash range, not creative or spectator.
- Vanilla chase cannot be pointed at an arbitrary target (L8); accept vanilla targeting for walking, keep attacks scripted.

## 8. Boss config format and module contracts

A boss config is a plain JS module exporting one object; a module is a class with a fixed shape. Both shapes below are proposals to finalise in milestone M1 and to type in `types/config.d.ts`.

### Config rules

- `schemaVersion` is required, so the format can evolve.
- Stay close to MythicMobs naming so a future YAML→JS generator stays mechanical.
- Inline functions are allowed **only** as custom conditions. Everything else goes through registered modules, so bosses do not bypass the module system.
- All durations in ticks.

### Example config (illustrative)

```
// bosses/darkknight.js
import anims from "../generated/darkknight/index.js";

export default {
  schemaVersion: 1,
  id: "forgotten:dark_knight",          // entity type ID
  display: { name: "Dark Knight", bossBar: true },
  stats: { health: 800, armor: 0, knockbackResist: 1, scale: 1.5 },
  animations: anims,                     // converter output
  ai: { default: "chase", leashRange: 40, resetAfterNoPlayers: 600 },
  threat: { enabled: true },
  // stats.healthScaling: { perPlayer: 0.25 }  (D7, decided)
  phases: [
    { id: 1, untilHealthPct: 50 },
    { id: 2, onEnter: ["phase2_roar"], properties: { "bhm:phase": 2 } }
  ],
  skills: {
    slam: {
      tr: "onTimer:100", if: ["distance<=4", "phase==1"], cooldown: 80, exclusive: true,
      c: [
        { m: "state", o: { anim: "attack_slam", lock: true } },
        { m: "waitMarker", o: { marker: "slam_impact" } },
        { m: "damage", o: { amount: 12 }, t: "@EntitiesInRadius{r=4}" },
        { m: "particleRing", o: { particle: "bhm:dust", radius: 4 }, t: "@SelfLocation" }
      ]
    },
    phase2_roar: { c: [ { m: "state", o: { anim: "roar" } }, { m: "setAI", o: { mode: "frozen", ticks: 40 } } ] }
  },
  drops: [ { item: "minecraft:diamond", amount: [2, 5], chance: 1 } ],
  requires: ["state", "damage", "particleRing", "setAI"]
};
```

### Module contracts (proposed)

| Module kind | Shape |
| --- | --- |
| Mechanic | `{ name, requires?, validate(options) → errors[], execute(ctx, targets, options) → void \| delayTicks }` |
| Targeter | `{ name, validate(options), resolve(ctx, options) → (Entity \| Location)[] }` |
| Condition | `{ name, validate(args), test(ctx, target, args) → boolean }`; negation handled by the executor |
| Trigger | `{ name, subscribe(bus) }`; emits `{ boss, triggerEntity, data }` |

`ctx` (execution context) carries: the boss instance, caster entity, trigger entity, current targets, variables, the cancel token and the adapter. Modules never call `@minecraft/server` directly; they use the adapter.

### Binding files

- `bosses/index.js`: one import + one `BossManager.bind(config)` line per boss.
- `registry/SkillManager.js`: one import + one `bind("name", Module)` line per module.

## 9. Converter tool

The converter is an offline Python CLI that turns a boss's model and animation files into everything the runtime needs, so no heavy work happens in-game. It is the biggest schedule risk because of the coordinate math (section 6). \[DECIDED: Python\]

### Inputs

- `*.geo.json` — bone hierarchy, pivots, rotations.
- `*.animation.json` — keyframes, interpolation modes, timelines.
- Optional `.bbmodel` — Blockbench timeline markers (effect / instruction channels) if not exported to Bedrock JSON.
- Which bones to bake: decided (D5) — the ones the YAML references, plus job `bone_aliases` / `blades`.
- Optional MythicMobs YAML (later milestone) for config skeleton hints.

### Processing

1. Parse geometry into a bone tree with pivots and rest rotations.
2. For each animation, compute length in ticks and loop flag.
3. Sample each tagged bone at every tick (forward kinematics): interpolate position / rotation / scale keyframes (linear, step, catmull-rom), compose transforms down the hierarchy, output the bone pivot in model space, converted to blocks (16 units = 1 block).
4. Evaluate Molang that depends only on `q.anim_time`; mark bones with any other Molang as unbakeable and warn.
5. Read timeline markers into `hitFrames` and named `markers`.
6. Emit outputs and a report.

### Outputs

- `generated/<boss>/<anim>.js` per animation, plus an `index.js` exporting all of them.
- **Entity patch report** (or direct patch): the section 5 stub — component groups, events, properties, damage sensor, boss component — and RP changes (render controller, `anim_time_update`).
- **Config skeleton** `bosses/<boss>.js`: states detected from animation names (idle, walk, attack\_\*, death, roar), stats placeholders, empty skills.
- **Report:** baked bones, unbakeable bones, animations without markers, warnings.

### Efficiency rules

- Bake only tagged bones; round to 3 decimals.
- Optionally sample every 2 ticks and interpolate at runtime if file size matters.

### Validation

- Unit tests against hand-checked bone positions for a simple test model (one arm, known rotation).
- In-game calibration with the bone-marker debug mode before trusting any boss.

## 10. State, lifecycle and edge cases

The boss entity is the source of truth: everything needed to resume a fight is stored on it as dynamic properties, and the in-memory instance is rebuilt whenever the entity loads.

### Lifecycle

1. **Spawn / load:** `entitySpawn` or `entityLoad` → look up config by type ID → create `BossInstance` → restore persisted state if present → fire `onSpawn` only for a fresh spawn.
2. **Active:** scheduler runs skills; event bus routes triggers.
3. **Unload:** chunk unloads → instance becomes invalid; scheduler drops its tasks. Every step checks `isValid` first.
4. **Reset:** no valid players within range for `resetAfterNoPlayers` ticks, or boss leaves `leashRange` → heal, phase 1, clear threat, return to spawn point.
5. **Death:** `entityDie` → cancel all tasks → `onDeath` skills → drops → delete instance.
6. **Minions \[DECIDED 2026-10-06\]:** configs carry `kind: "boss" | "minion"` (default boss; the converter writes it). Minions are driven exactly like bosses but are never listed or edited in the menu. Summons are bound to their boss by default (`summon{bind}`, persisted) and removed when it dies, despawns or resets.
7. **Known bosses:** the world property `bhm:known` records every boss (type, name, dimension, position; flushed every 5 s) so the menu's "Bosses in world" list can show unloaded ones, nearest first, with teleport.

### What is persisted

Phase, spawn/arena point, cooldown end ticks (stored relative to world tick), variables, threat table (optional). Size limit of dynamic properties \[VERIFY\].

### Multiplayer

- Targeters exclude creative and spectator players.
- Handle players dying, respawning, logging out or changing dimension mid-fight (drop from threat table).
- Health scaling by player count \[DECIDED 2026-10-06, D7\]: config `stats.healthScaling { perPlayer, radius?, max? }` → effective health × (1 + perPlayer × (players − 1)), counting targetable players near the boss; set on spawn and reset, only rises during a fight, persisted (L38).
- Drops \[DECIDED 2026-10-06, D7\]: everything goes into a **loot chest** placed on the ground where the boss died (more chests beside it if needed), so players share it out themselves. Loot chests are protected from explosions (a boss exploding on death, creepers, TNT) through the explosion before-event until a player breaks them; the list is persisted in `bhm:lootchests`. `loot.mode: "ground"` drops items instead.
- `playAnimation` can target a player list; default to all players.

### World and gameplay rules

- **Peaceful difficulty** \[DECIDED 2026-10-06, D6\]: the framework removes bosses and minions (checked every second) and refuses new spawns; `allowPeaceful: true` opts out.
- **mobGriefing** gamerule affects block-changing skills; check it.
- **Difficulty scaling of `applyDamage`** is unknown \[VERIFY by test\].
- **Ticking areas:** capped (believed 10) \[VERIFY\]; decide behaviour when a fight's chunk unloads.
- **Multiple bosses** at once are supported by design (instance per entity ID).
- **Other addons and `/kill`:** treat unexpected removal like death without drops.

### Drops and items

- Simple drops: rolled from config `drops`, put into the loot chest (D7) or, with `loot.mode: "ground"`, spawned as items.
- MythicMobs `drops.yml` maps only partly. Custom items with abilities are out of v1.

## 11. Performance, tooling and testing

Performance is budgeted per boss per tick, and debug tools are built before features, because the main risks (bone math, skill timing) are only visible in-game.

### Performance rules

- One scheduler loop for the whole framework; no per-skill `runInterval` and no nested `runTimeout` chains.
- Target CPU budget per boss per tick \[OPEN, D8: deferred — the owner's machine is too fast to measure a meaningful budget; revisit on weaker hardware\].
- `system.runJob` (generator functions) for heavy work such as large particle shapes.
- **Particle culling:** spawn only when a player is within a set range; cap particles per tick per boss. Mobile and console players hit limits first.
- Summon caps per boss and globally.
- Pre-parse configs once at startup; cache targeter results within a single skill step.
- Profile with whatever profiling support the current Script API version offers \[VERIFY\].

### Developer tooling

- **`/behemoth` menu** (single custom command `bhm:behemoth`, operators, no cheats needed; chest UI with a gray/black glass border): settings (debug overlay, log level, bone markers, hitbox preview, seeded RNG, icon set, performance), boss list (spawn), nearest boss (reset, despawn, phase ±, cast skill), boss packs, diagnostics (script-event probe, cache), about. Settings persist in the world.
- **Debug overlay** (action bar or particles): phase, active skills, cooldowns, top threat.
- **Bone markers:** particle at each baked bone position every tick (calibration).
- **Log levels:** error / warn / info / debug, prefixed `[BHM]`.

## 12. Coverage and similarity estimates

A typical purchased boss should feel like the same fight with slightly rougher edges; bosses built around ModelEngine tricks lose the most. These are judgement-based planning estimates, not measurements.

| Scope | Estimate | Reason |
| --- | --- | --- |
| MM features real boss packs use | \~85–90% | Damage, AoE, projectiles, leaps, summons, phases, cooldowns, animation states all map cleanly. |
| MythicMobs as a whole | \~55–65% | Many features are Java-server-specific (items/Crucible, disguises, holograms, placeholders, packets, economy, GUIs). |
| ModelEngine features | \~60–70% | Animations and bone effects work; hitboxes approximated; segmented bodies and bone mounts mostly out. |
| Logic and timing similarity | \~90–95% | Both run on 20 TPS ticks. |
| Combat feel, typical boss | \~75–85% | Weaker navigation, \~0.1–0.3 block hit drift, particle differences, fixed boss bar. |
| Combat feel, ModelEngine showpiece bosses | \~50–60% | Multi-part bodies and part hitboxes are noticeable losses. Redesign or skip these. |

## 16. Future companion frameworks

Companion frameworks should reuse Behemoth's adapter, scheduler and module registry rather than duplicate them. Candidates, roughly by value:

| Candidate | What it does | Builds on |
| --- | --- | --- |
| YAML → JS generator | Converts MythicMobs YAML into Behemoth configs; flags unsupported mechanics. | Config schema, converter |
| Mythic Items (Crucible-like) | Custom items with skills, triggers on use/hit, cooldowns. | Skill executor, mechanics, triggers |
| Arena / encounter framework | Arenas, spawn conditions, wave encounters, entry gates, rewards, leaderboards. | Boss lifecycle, event bus |
| Model tools | Blockbench plugin or script to tag bones, add markers, validate animations for the converter. | Converter |
| Particle / VFX library | Reusable shaped effects (beams, shockwaves, slashes) with budgets. | Shared RP particles, scheduler |
| Drop / loot framework | Contribution-based drops, rarity tables, custom-named items. | Threat table |
| Ability framework for players | Player-side skills using the same modules (overlaps with the earlier mob-skills addon). | All registries |

## 17. Conventions and handoff notes

Anyone continuing this project, human or AI, should follow these rules so the codebase stays consistent with this document.

### Working rules

- Read sections 3, 13, 14 and 15 before writing code; check which milestone is current.
- Never invent Script API names. Anything not confirmed in the current typings is flagged **\[VERIFY\]** in code comments and in replies, so the owner can check via IDE autocomplete.
- Deliver complete, runnable files rather than diffs or partial snippets; no leftover debug output.
- Modules call the adapter, never `@minecraft/server` directly.
- Mechanics and conditions stay stateless; state lives in the boss instance or `ctx`.
- Every scheduled task carries the boss instance's cancel token.
- Every new platform limit found → new row in section 3 with a workaround.
- Every new decision → move it from section 15 to the relevant section, marked \[DECIDED\].
- Stable APIs only.

### Naming

- Framework identifiers, events, groups and properties: `bhm:` prefix.
- Baked bones: `bhm_` prefix (if D5 chooses the convention).
- Animation controllers: `bhm_base`, `bhm_action`, `bhm_overlay`.
- Files: `snake_case.js` for modules and configs; `PascalCase.js` for core classes.
- Logs: `[BHM]` prefix with level.
- Time values: ticks everywhere; name fields `...Ticks` where ambiguous.

### Owner context

- The owner is an experienced developer (Python full-stack) who has built Bedrock Script API addons before, including a scripted boss (Knight of the Lost Dimension), a mob-skills system, and Forge/Fabric mods.
- Troubleshooting is iterative: exact error messages and IDE screenshots are shared.

### Document maintenance

Update the as-of date when the doc changes. Keep sections in this order; add new material to the matching section instead of appending at the end.
